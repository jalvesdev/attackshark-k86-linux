# Correção 6.3 — metadados de coleção HID no Fedora

## Diagnóstico

Na enumeração fornecida pelo Fedora para VID:PID `3151:4015`, as interfaces 0, 1 e 2 aparecem com `usage_page=0`, `usage=0`, `bus_type=1` e strings de fabricante/produto vazias. O hidapi Python instalado no ambiente é 0.15.0.

No backend Linux do hidapi, os metadados de uso são derivados do descritor HID encontrado em sysfs. O registro é inicializado sem uso conhecido; a página e o uso são preenchidos quando o descritor é lido e seu par de coleção é interpretado. Assim, `0/0` não é prova suficiente de incompatibilidade: é metadado inconclusivo (e, isoladamente, não permite distinguir ausência de parsing de um descritor que declare valores sem utilidade). As strings vazias também não provam identidade nem incompatibilidade. A implementação não as usa para autorizar acesso.

Fonte de implementação consultada: [hidapi 0.15.0, backend Linux `hid.c`](https://github.com/libusb/hidapi/blob/hidapi-0.15.0/linux/hid.c). O backend associa o `report_descriptor` ao caminho sysfs da coleção HID. O kernel documenta esse atributo como o descritor bruto, disponível em sysfs para dispositivos HID: [ABI sysfs `report_descriptor`](https://github.com/torvalds/linux/blob/master/Documentation/ABI/testing/sysfs-driver-hid) e [introdução HID do kernel](https://kernel.org/doc/html/latest/hid/hidintro.html).

## Validação implementada

1. O hidapi enumera VID `3151`, PID `4015`; somente interface USB 2 é candidata. A seleção não usa interface alternativa nem caminho `hidrawN` fixo. Quando disponível, o tipo de barramento deve ser USB (`1`).
2. Se hidapi informar um uso, ele deve ser `FFFF:0002`. O par `0/0` é aceito apenas como ausência/inconclusão para permitir a validação seguinte; não basta para abrir uma conexão utilizável.
3. Antes de devolver `K86Client.open()`, o descritor deve comprovar coleção `FFFF:0002` e Feature Report de 64 bytes com Report ID 0. Quando o binding expõe o descritor, ele é lido do handle que acabou de abrir. Caso contrário, em Linux, o path enumerado é resolvido dinamicamente em sysfs.
4. Para o fallback sysfs, o código verifica `idVendor`, `idProduct` e `bInterfaceNumber` da mesma interface. O nó HID deve estar abaixo dessa interface e seu `uevent` deve declarar `HID_ID=0003:00003151:00004015`. Só então é lido seu `report_descriptor`. Não conseguir estabelecer essa cadeia de identidade causa erro diagnóstico e bloqueia o acesso.
5. `K86Client.open(selected=...)` só aceita um registro igual a uma única linha da enumeração atual; registros externos, obsoletos ou ambíguos são recusados antes de abrir o path.

`usage_page`/`usage` de hidapi, VID:PID, interface, barramento e descritor validam identidade USB/HID e coleção. O ID interno 1168 ainda depende da resposta da consulta `0x8F` na conexão. A associação `1168 → yc500` continua sendo a correspondência do catálogo sharkfin, não uma propriedade inferida do descritor. Nenhum relatório Feature foi enviado para produzir esta correção.

## Regressão e escopo

As fixtures sysfs são sintéticas: modelam as relações de symlink de USB/HID e os atributos do kernel com os metadados relatados pelo Fedora, sem acessar `/sys` da máquina nem o teclado. Os testes verificam `0/0` e strings vazias, descritor certo, descritor/uso incompatível, interface/USB incorretos e resolução dinâmica de path USB e hidraw. Um teste adicional impede que `open(selected=...)` contorne a enumeração atual. Nesta retomada, a suíte completa passou: **33 testes** com `.venv/bin/python -m unittest discover -s tests -v`; `compileall`, simulação identify e `tools/read_active_profile.py --help` também passaram. Nenhum teste abriu o HID físico.

## Limites

O fallback exige visibilidade e leitura do descritor sysfs pelo usuário atual. Se o kernel, binding ou layout sysfs não oferecer os atributos esperados, a ferramenta falha fechada. Identificadores USB e o descritor são evidência da interface, mas não provam criptograficamente autenticidade do fabricante ou do firmware. A identificação interna `0x8F` e a checagem do valor 1168 permanecem necessárias antes de qualquer GET de configuração.
