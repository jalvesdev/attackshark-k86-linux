# Ciclo 6.5 — integração da consulta de perfil ativo

## Causa raiz e alcance da tentativa anterior

`tools/read_active_profile.py` usa `K86Client.open()` para manter uma sessão e acessar `HidConnection.feature_roundtrip()` em sequência. Os dados da última troca são armazenados em `HidConnection.last_exchange`; `K86Client` não declara esse atributo. A API do cliente não foi alterada no ciclo 6.4: a exceção era uma referência incorreta na integração do script.

Na tentativa registrada na última linha de `docs/06-profile-hardware.jsonl`, a seleção, abertura e validação do descritor já haviam sido concluídas. A exceção ocorre na instrução seguinte ao retorno de `feature_roundtrip(0x8F)`. Portanto, a evidência do log e a ordem do código indicam que o roundtrip de identificação foi concluído antes da exceção. O log não contém os bytes TX/RX porque a tentativa de preencher esses campos falhou ao acessar `client.last_exchange`. Não é possível reconstruir do JSONL o conteúdo transmitido ou recebido. A execução parou antes da validação do ID e antes da consulta `0x85`; não há evidência de que `0x85` tenha sido enviado.

O JSONL anterior foi preservado sem alterações. Nenhuma consulta física foi executada durante o ciclo 6.5.

## Correção

O script agora captura `connection.last_exchange` após cada chamada, inclusive quando a chamada termina em exceção. Só registra uma troca se o objeto tiver sido atualizado para o opcode esperado. TX vem do registro do transporte; RX é omitido quando a camada de transporte não obteve resposta. O resultado só recebe `success` depois de identificar o ID 1168, obter uma resposta válida de `0x85` e decodificar o índice do perfil.

Não foi adicionado estado a `K86Client`, não houve mudança no backend hidraw, nem foi criada uma nova camada de transporte. A validação do identificador interno continua precedendo a consulta de configuração.

## Validação simulada

Os testes de integração usam `K86Client` e `HidConnection` reais com backend e handle HID falsos. A resposta de identificação é a fixture física já preservada no repositório; a resposta de perfil é sintética e identificada como tal nos testes. O cenário de sucesso comprova a ordem `0x8F` seguida por uma única `0x85`, TX/RX associados a cada opcode e decodificação do índice. O cenário de timeout simulado comprova que TX/outcome são registrados, RX/perfil não são inventados e o resultado não é sucesso.

Os testes não acessam o teclado nem enviam Feature Reports físicos. A resposta sintética não é evidência sobre o perfil atual do hardware.

## Próxima validação física

Depois de decidir iniciar a validação no Fedora, execute uma única vez:

```sh
.venv/bin/python tools/read_active_profile.py --timeout 2 --log docs/06-profile-hardware.jsonl
```

O procedimento realiza identificação `0x8F`, exige ID 1168 e só então emite uma consulta `0x85`. Não repete automaticamente. Em caso de falha, preserve a nova linha JSONL e investigue antes de qualquer nova tentativa. O comando não foi executado durante o trabalho de correção 6.5.

## Registro físico posterior

O JSONL local agora contém uma execução posterior registrada como sucesso: interface 2, descritor `FFFF:0002` com Feature Report ID 0 de 64 bytes, resposta de identificação decodificada como ID 1168 e resposta `0x85` decodificada com índice de perfil ativo `0`. A resposta foi validada pelo opcode e pelo comprimento de relatório usados pelo codec. Esse registro é evidência de uma execução física posterior à correção; não foi produzido pela suíte simulada, que escreve em arquivo temporário. O JSONL bruto foi preservado localmente e ficou fora do commit para não versionar path hidraw e tráfego bruto do dispositivo.
