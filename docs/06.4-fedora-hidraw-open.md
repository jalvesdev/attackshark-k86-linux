# Abertura do K86 no Fedora — correção do backend HID

## Sintoma e evidência disponível

O Fedora enumerou o dispositivo `3151:4015`, interface 2, com `path=b'1-1.2:1.2'`. `hid.device().open_path()` devolveu `OSError: open failed`, mas `os.open('/dev/hidraw3', O_RDWR | O_NONBLOCK)` funcionou sob a ACL já aplicada à interface. O número `hidraw3` é dinâmico e não é usado pelo código.

No ambiente `.venv` inspecionado, `hid` é o módulo `hidapi` 0.15.0. O binário ELF `hid.cpython-314-...so` depende da libusb empacotada e importa `libusb_open`/`libusb_claim_interface`. A mesma distribuição inclui `hidraw.cpython-314-...so`, que depende de libudev e usa `ioctl`, sem dependência de libusb. O backend libusb gera paths do tipo barramento/portas/configuração/interface (o código upstream usa esse formato); o backend hidraw abre paths de nó como `/dev/hidrawN`. As APIs Python mantêm o mesmo formato de `enumerate`, `device.open_path`, leitura do descritor e fechamento.

Fontes: [distribuição Python hidapi 0.15.0 e opções Linux](https://pypi.org/project/hidapi/0.15.0/), [wrapper Cython `open_path` e `get_report_descriptor`](https://github.com/trezor/cython-hidapi/blob/master/hid.pyx), [backend libusb do hidapi](https://github.com/libusb/hidapi/blob/hidapi-0.15.0/libusb/hid.c) e [backend hidraw Linux](https://github.com/libusb/hidapi/blob/hidapi-0.15.0/linux/hid.c).

## Causa raiz e grau de certeza

**Confirmado:** o código anterior importava `hid`, e portanto usava neste ambiente o módulo compilado com libusb. A evidência de ACL cobre o nó `/dev/hidrawN`, não comprova acesso ao dispositivo USB via USBFS. O path `1-1.2:1.2` não é o path do nó hidraw. Logo a aplicação tentava abrir com backend/permissão diferentes daqueles que o teste positivo `os.open` validou. A wrapper Cython converte qualquer falha nativa de `hid_open_path` na mensagem genérica `open failed`, então o texto observado não revela o errno subjacente.

**Não confirmado:** não sabemos se a falha nativa específica foi acesso negado ao nó USBFS, interface ocupada pelo driver `usbhid`, ou outra condição libusb. A solução não depende de adivinhar entre essas hipóteses: ela usa o backend hidraw correspondente ao nó para o qual a ACL já foi concedida.

## Correção

- No Linux, `HidApiBackend` importa `hidraw` da própria distribuição `hidapi`; enumeração e abertura usam a mesma implementação. O restante do transporte e da arquitetura não ganhou um segundo driver de projeto. Se a extensão não estiver presente, a inicialização falha com diagnóstico explícito; não há fallback silencioso para libusb.
- O pacote mínimo passou a `hidapi>=0.15`, que é a versão comprovada neste ambiente e inclui a extensão hidraw. Windows/macOS continuam usando `hid`.
- O path é sempre o retornado na enumeração hidraw. Seleção ainda exige exatamente VID `3151`, PID `4015`, interface USB 2, barramento USB e coleção compatível; a validação do descritor obtido do handle/sysfs continua obrigatória. Interfaces 0/1 não são fallback.
- O binding Python real implementa `get_report_descriptor()` sem argumentos. O transporte agora aceita essa assinatura (além de assinaturas antigas por tamanho/buffer), evitando que a validação falhe com `TypeError` depois de uma abertura bem-sucedida.
- Erros de abertura são distinguidos: permissão, desaparecimento do nó após enumeração e falha de abertura não classificada. O wrapper hidapi pode ocultar o errno; quando disponível, a mensagem global `device.error()` é incluída. `DeviceNotFound` continua indicando ausência na enumeração.

## Testes e segurança

Testes unitários usam um módulo hidraw falso, caminhos dinâmicos como `/dev/hidraw43`, metadados sintéticos para interfaces 0/1/2, falhas de permissão/desaparecimento/abertura genérica e um descritor acessível sem argumentos. O caso de abertura/fechamento verifica que interface 2 é aberta, que o handle fecha e que nenhum método de envio é chamado. Eles não enumeram nem abrem um dispositivo real.

O teste físico posterior é estritamente abrir, validar descritor e fechar. Não chama `identify`, `read_yc500`, `send_feature_report` ou `get_feature_report`. Execute no Fedora com `.venv` instalado e ACL já configurada, sem `sudo`:

```sh
.venv/bin/python - <<'PY'
from attackshark_k86.transport import K86Client

with K86Client().open() as connection:
    print(f"aberto: VID:PID 3151:4015, interface {connection.device.interface_number}, path {connection.device.path!r}")
print("handle fechado")
PY
```

Sucesso: imprime interface 2 e path dinâmico `/dev/hidrawN`, em seguida `handle fechado`, sem relatório transmitido. Qualquer erro encerra antes de qualquer troca HID; não repita automaticamente. Registre a classe/mensagem da exceção, preserve o número de `hidraw` como dado de diagnóstico daquela execução e verifique em uma etapa separada se a ACL permanece restrita à interface 2. Nenhum teste de perfil faz parte deste procedimento.

## Limites remanescentes

Após a correção, o operador confirmou abertura física e fechamento com sucesso: `VID:PID 3151:4015`, interface 2, path dinâmico `/dev/hidraw3`, seguido de `handle fechado`. Isso confirma abertura e fechamento no host naquele momento; não confirma por si só o ID interno nem a família yc500, que dependem da identificação `0x8F`. Os dois registros `open failed` anteriores em `docs/06-profile-hardware.jsonl` não têm campos `identify_tx` ou `profile_tx`, portanto representam falhas anteriores à abertura/transmissão. Uma tentativa posterior registrada nesse JSONL contém as trocas `0x8F` e `0x85`; o estado dessa leitura está documentado em [`06.5-profile-integration.md`](06.5-profile-integration.md).
